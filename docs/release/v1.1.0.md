# lock-db v1.1.0

A minor release with fixes from an independent review. The deadlock-aware path
no longer serializes on one global mutex or rebuilds the wait-for graph on
every call, a deadlock victim is fenced until it has rolled back, and `request`
grants in first-in, first-out order. Everything is additive to the 1.0 API, and
the MSRV stays at 1.85.

## What changed

### Deadlock detection cost

In 1.0 every `request` took one global mutex, and every conflicting call rebuilt
the whole wait-for graph from all waiters in the system while holding it.
`find_deadlock` restarted its search from every waiter, so a wait chain cost
quadratic time, again under that mutex.

1.1 removes the global wait mutex. Each transaction's pending wait lives in a
small table sharded by transaction id. Detection at the moment of a wait walks
only the edges reachable from the new waiter, reading each waiter's edges from
the lock table as the walk reaches it, and holds no lock across the walk.
`find_deadlock` and `WaitForGraph::detect_cycle` share one visited set across
every start, so they are linear in the size of the graph.

### Victim fencing

When a deadlock check names a victim that is not the requesting transaction,
the victim's own thread is not told by that call. In 1.0 nothing marked it, so
after the requester released it, the victim's next `request` was granted fresh
locks while it still believed it held the ones it had lost.

1.1 marks the victim. Its next `request` returns `Acquisition::Deadlock` naming
itself, and its next `try_acquire` / `try_acquire_range` returns the new
`LockError::Aborted`. The new `LockManager::is_aborted` lets it ask directly.
Releasing it from another thread frees its locks but keeps the mark; the
victim's own `release_all` clears it (the first one after it was told, or the
second release since it was marked, so a victim that gives up without asking
leaves nothing behind). While the mark is
set, `release_all` sweeps every shard, so a lock the victim took concurrently
cannot be missed.

### First-in, first-out fairness for `request`

In 1.0 a grant looked only at current holders, so a writer waiting for X behind
a reader was overtaken by every newer reader and could wait forever. 1.1 keeps
a wait queue per resource. A `request` is granted only when it is compatible
with every holder and with every transaction queued ahead of it. Transactions
that already hold the resource and ask for more (upgraders) queue ahead of
those that hold nothing. Queue order also feeds detection: a waiter waits for
the conflicting waiters ahead of it, so a cycle through a queue is found.

`try_acquire` is unchanged and does not consult the queue.

### Smaller fixes

- `release_all` visits only the shards the transaction holds locks in, tracked
  per transaction, instead of every shard (up to 1,024 on a large machine).
- Re-acquiring a range lock is idempotent: inside a range already held in a
  covering mode it changes nothing, and on exactly a held range it upgrades in
  place. In 1.0 each call added a holder.
- Documentation corrected: the module docs, the precondition of exact
  detection (abandoned waits must be cleared), the cost of `release_all`, the
  README's claim that txn-db, page-db, and index-db use lock-db (none does),
  `LockMode`'s `Ord` (declaration order, not the privilege lattice), and the
  id-as-age note on `VictimPolicy`.

## Behavior changes to note

These are the only places where a 1.0 caller can observe a difference:

- A `request` that 1.0 granted by overtaking a queued, conflicting waiter now
  returns `Waiting`. A waiter must eventually be granted, call `cancel_wait`, or
  be released, or it blocks the transactions queued behind it.
- A transaction named as a deadlock victim is refused until it calls
  `release_all` on itself after being told.
- Re-acquiring the same range twice leaves one lock, so one `release_range`
  frees it.

No public item was removed or changed in signature. `LockError` is
`#[non_exhaustive]`, so the new `Aborted` variant is additive.

## Measurements

Review repros, release build, Windows x86_64 on a shared, loaded 32-thread
machine. Single runs; the growth rates are the point.

| Measurement | 1.0.0 | 1.1.0 |
|---|---|---|
| conflicting `request`, 0 unrelated waiters | 0.88 us | 0.78 us |
| conflicting `request`, 100 unrelated waiters | 22 us | 0.75 us |
| conflicting `request`, 1,000 unrelated waiters | 281 us | 0.67 us |
| conflicting `request`, 5,000 unrelated waiters | 952 us | 0.71 us |
| `find_deadlock`, acyclic chain of 500 | 18.7 ms | 0.17 ms |
| `find_deadlock`, acyclic chain of 1,000 | 53.5 ms | 0.35 ms |
| `find_deadlock`, acyclic chain of 2,000 | 234 ms | 0.74 ms |
| acquire 1 lock + `release_all`, 16 shards | 1.5 us | 0.23 us |
| acquire 1 lock + `release_all`, 128 shards | 9.6 us | 0.26 us |
| acquire 1 lock + `release_all`, 1,024 shards | 39 us | 0.39 us |

Fast paths, measured in one process that links both versions and alternates
them, five rounds each, medians:

| Operation | 1.0.0 | 1.1.0 |
|---|---|---|
| `try_acquire` + `release` (only lock in its shard) | 227 ns | 293 ns |
| `request` granted + `release` | 247 ns | 287 ns |
| 4 locks + `release_all`, 128 shards | 5.4 us | 1.0 us |
| range acquire + release against 1,024 live ranges | 1.60 us | 1.52 us |

The one cost is on a transaction's first lock in a shard and its last release
there: recording which shards it uses takes a second, sharded mutex, about
50 to 70 ns on this machine. That record is what lets `release_all` skip every
shard the transaction never touched.
